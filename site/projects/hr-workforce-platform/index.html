Case study

HR & Workforce Management Platform

A bilingual ERP for HR and employee management — 35 screens covering employee administration, multi-level approval workflows, shift scheduling and reporting. In production and in daily use.

The problem

The client was running HR administration across spreadsheets and email. Leave requests, overtime claims, missing-punch corrections and business-trip approvals all travelled as mail threads, which meant no reliable audit trail, no visibility into where a request was stuck, and monthly reconciliation done by hand against fingerprint-terminal exports.

The requirement was a single system that could model the organisation's real approval hierarchy, enforce it reliably, and remain usable by staff in both English and Arabic.

Approach

I modelled and diagrammed the approval workflows with stakeholders before writing any code, so that state transitions and escalation paths were agreed while they were still cheap to change. That produced the core abstraction the system is built around: a request is a state machine, and every request type — leave, overtime, missing punch, business trip — moves through the same engine with a different policy attached.

Multi-level approval engine

Requests escalate from the direct manager (N+1) to their manager (N+2) and on to HR, with timed reminders at each stage. Because the escalation path is derived from the organisation structure rather than hard-coded, a reporting-line change takes effect without a deployment.

Access control in the database, not the client

Every table is protected by PostgreSQL Row Level Security. The client application holds no authority of its own: an employee querying the employee table receives their own row and their reports' rows because the policy says so, not because the UI filtered the list. This was a deliberate choice — it means a bug in a Flutter screen cannot become a data breach.

Notification layer

Approval mail is sent from Supabase Edge Functions running on Deno, authenticating to the Gmail API through OAuth 2.0 implemented inside the function. Each stage of a request produces a templated HTML email with the context the approver needs to decide without opening the app.

Bilingual by construction

The interface is fully localised in English and Arabic, including right-to-left layout. Handling RTL as a first-class case from the start — rather than retrofitting it — is what kept the scheduling and org-chart screens workable in both directions.

The hard parts

Migrating authentication with no downtime. The system originally used a custom authentication scheme. Moving it onto Supabase Auth meant verifying JWTs inside Edge Functions and migrating existing users on the fly, at first login, so that active accounts kept working throughout the transition.

A trigger that silently ate writes. Certain updates were being applied partially, with no error surfaced anywhere. The cause was a database trigger overriding client-supplied columns during an update. Finding it changed how I test this system: RLS policies and triggers are now exercised directly against the database, not inferred from application behaviour.

Keeping the data layer swappable. Every repository in the app is defined as an abstract interface with a Supabase implementation behind it, wired through a single dependency-injection point. That discipline was originally about testability — but it is also what made the demo on this site achievable, since substituting in-memory implementations swapped out the entire backend without touching a single screen.

Try it

The demo is the real application with its data layer replaced by seeded, fictional records. You can switch between employee, manager and HR roles to see the same request from each side of an approval chain.
